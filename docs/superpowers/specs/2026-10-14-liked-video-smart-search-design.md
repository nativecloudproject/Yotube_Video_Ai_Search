# TubeLite 좋아요 영상 스마트 검색 설계

## 배경

TubeLite는 Flask, SQLite, React로 구성된 로컬 유튜브 클론이다. 로그인, 업로드, 시청, 좋아요, 댓글, 구독과 보관함 기능은 이미 있지만 좋아요 영상 검색은 두 구현으로 갈라져 있다.

- 현재 프런트엔드 소스는 고정 카테고리 사전과 부분 문자열 비교를 브라우저에서 수행한다.
- 백엔드의 `/api/recommend/`는 TF-IDF 유사도를 계산하지만 사용자의 좋아요 범위가 아니라 전체 영상을 대상으로 한다.
- 커밋된 `static/app` 빌드는 이전 `/recommend` 화면을 포함해 현재 프런트엔드 소스와 다르다.
- 자동화 테스트와 재현 가능한 스마트 검색 검증이 없다.

이 설계는 TubeLite 내부에서 사용자가 좋아요한 영상만 대상으로 하는 로컬 스마트 검색을 하나의 백엔드 계약으로 통합한다.

## 목표

1. 로그인 사용자가 자신의 좋아요 영상에서 자연어 키워드로 관련 영상을 찾는다.
2. 검색 순위는 제목, 설명, 채널명을 이용한 가중 TF-IDF와 코사인 유사도로 결정한다.
3. 백엔드가 사용자 범위 제한과 순위 계산의 유일한 기준이 된다.
4. 검색어, 결과 수, 유사도, 일치 단어와 일치 영역을 화면에서 이해할 수 있다.
5. 로그인부터 검색까지 Flask 단일 로컬 서버에서 실행되며 프런트엔드 소스와 정적 빌드가 일치한다.
6. 검색 엔진, API, 핵심 React 흐름에 회귀 테스트를 제공한다.

## 비목표

- 실제 YouTube 계정, Google OAuth 또는 YouTube Data API 연동
- 클라우드 배포, S3, DynamoDB, SNS, EventBridge 또는 외부 벡터 데이터베이스
- 외부 임베딩 API, 대형 언어 모델, PyTorch 또는 런타임 모델 다운로드
- 자막 추출, 음성 전사 또는 영상 픽셀 분석
- 대규모 데이터용 ANN 인덱스와 분산 검색

## 성공 기준

- `/liked`에서 검색어를 제출하면 현재 사용자가 좋아요한 영상만 관련도순으로 표시된다.
- 한 사용자의 검색 응답에 다른 사용자의 비공개 좋아요 관계가 반영되거나 노출되지 않는다.
- 공백 검색, 좋아요 없음, 일치 결과 없음, 인증 실패, 잘못된 입력과 서버 오류가 각각 명확하게 처리된다.
- 검색어가 `/liked?q=...`에 유지되어 새로고침과 브라우저 앞/뒤 이동 후에도 같은 검색이 복원된다.
- 백엔드 전체 테스트, 프런트엔드 전체 테스트와 프런트엔드 프로덕션 빌드가 통과한다.
- 생성된 `static/app`으로 실행한 Flask 서버에서 데모 계정의 로그인, 좋아요 목록과 스마트 검색을 브라우저로 확인할 수 있다.

## 전체 구조

기존 Flask 모놀리스와 React SPA를 유지한다. 별도 서비스나 프로세스는 추가하지 않는다.

```text
/liked?q=개발
  -> React Library 화면
  -> GET /api/recommend/liked?q=개발&limit=24
  -> 세션 사용자 확인
  -> SQLite에서 사용자가 좋아요한 영상만 선택
  -> 순수 Python 검색 엔진이 TF-IDF 및 코사인 유사도 계산
  -> 점수, 일치 단어, 일치 영역이 포함된 JSON
  -> 관련도순 영상 카드와 검색 근거 표시
```

### 컴포넌트 경계

`features/recommend/search.py`

- Flask, 세션, SQLite에 의존하지 않는 순수 검색 모듈이다.
- 정규화, 토큰화, TF-IDF 벡터화, 코사인 유사도, 검색 근거와 안정 정렬을 담당한다.
- 입력은 일반 영상 딕셔너리 목록과 검색어이며, 출력은 영상과 검색 메타데이터의 목록이다.

`features/recommend/api.py`

- `GET /api/recommend/liked`를 제공한다.
- 인증, 입력 검증, 현재 사용자 좋아요 범위 선택, 검색 모듈 호출과 공개 응답 직렬화를 담당한다.
- 원본 `likes`와 `dislikes` 배열은 응답에 포함하지 않는다.

`frontend/src/features/videos/Library.jsx`

- 다른 보관함 화면의 기존 동작을 유지하면서 `kind === "liked"`일 때 새 검색 API를 사용한다.
- URL 검색어, 입력 상태, 로딩, 오류, 빈 상태, 결과 수와 검색 근거를 표현한다.
- 검색 순위를 다시 계산하지 않는다.

`frontend/src/features/recommend/routes.jsx`

- 이전 북마크와 커밋된 옛 화면을 위해 `/recommend`를 `/liked`로 이동시키는 호환 라우트만 제공한다.
- 기존 검색어가 있으면 리다이렉트 후에도 유지한다.

`app.py`와 `core/db.py`

- `create_app(config=None)` 앱 팩토리와 테스트용 데이터베이스 경로 주입을 제공한다.
- `python app.py` 실행 방식과 기능 Blueprint 자동 등록은 유지한다.
- 주기 작업은 직접 실행할 때만 시작하며 테스트 앱에서는 시작하지 않는다.

## 검색 알고리즘

### 정규화와 토큰

1. 입력을 Unicode NFKC로 정규화하고 소문자로 변환한다.
2. 한글, 영문자와 숫자로 구성된 단어만 추출한다.
3. 각 단어 자체와 단어 내부의 문자 2-gram을 검색 토큰으로 사용한다.
4. 공백과 구두점만 있는 검색어는 빈 검색으로 취급한다.

문자 2-gram은 별도 형태소 분석기 없이도 한국어 활용형과 부분 단어의 겹침을 찾기 위한 장치다. 고정 카테고리 사전은 사용하지 않는다.

### 필드 가중치

각 영상의 검색 문서는 필드별 토큰 빈도에 다음 가중치를 적용해 합친다.

| 필드 | 가중치 |
|---|---:|
| 제목 | 3.0 |
| 설명 | 1.5 |
| 채널명 | 1.0 |

IDF는 현재 사용자가 좋아요한 후보 영상 집합을 기준으로 계산한다. 검색어와 각 후보의 TF-IDF 벡터 간 코사인 유사도를 `0.0`에서 `1.0` 사이 점수로 반환한다.

### 필터와 정렬

- 검색어가 비어 있으면 전체 좋아요 영상을 생성일 내림차순으로 반환하고 `score`는 `null`이다.
- 검색어가 있으면 점수가 `0`보다 큰 영상만 포함한다.
- 기본 결과 제한은 24개이고 허용 범위는 1개에서 50개다.
- 기본 정렬은 점수 내림차순, 생성일 내림차순, 영상 ID 오름차순이다.
- `total`은 결과 제한을 적용하기 전 일치한 영상 수다.

### 검색 근거

각 결과에는 다음을 포함한다.

- `score`: 소수점 네 자리로 반올림한 코사인 유사도
- `matched_terms`: 원래 검색어의 단어 중 해당 영상 점수에 기여한 단어
- `matched_fields`: `title`, `description`, `channel` 중 토큰 겹침이 발견된 영역

문자 2-gram 자체를 사용자에게 나열하지 않고, 그 2-gram을 만든 원래 검색 단어를 표시한다.

## API 계약

### 요청

```http
GET /api/recommend/liked?q=%EA%B0%9C%EB%B0%9C&limit=24
```

- 세션 로그인이 필수다.
- `q`는 앞뒤 공백 제거 후 최대 100자다.
- `limit`은 선택적인 정수이며 기본값은 24, 범위는 1부터 50이다.

### 성공 응답

```json
{
  "query": "개발",
  "total": 2,
  "items": [
    {
      "id": "video-id",
      "title": "파이썬으로 게시판 만들기",
      "desc": "Flask와 SQLite로 구현합니다.",
      "uploader": "choi",
      "uploader_name": "최도윤",
      "thumb_url": "/uploads/example.png",
      "file_url": "",
      "duration": 1810,
      "views": 7300,
      "like_count": 3,
      "dislike_count": 0,
      "my_reaction": "like",
      "channel": {
        "id": "choi",
        "name": "최도윤",
        "color": "#606060"
      },
      "score": 0.6421,
      "matched_terms": ["개발"],
      "matched_fields": ["title", "description"]
    }
  ]
}
```

### 오류 응답

- 로그인 없음: `401 {"error": "로그인이 필요합니다."}`
- 검색어 100자 초과: `400 {"error": "검색어는 100자 이하여야 합니다."}`
- `limit`이 정수가 아니거나 범위를 벗어남: `400 {"error": "limit은 1부터 50 사이의 정수여야 합니다."}`
- 예상하지 못한 오류: 기존 JSON 오류 처리 규칙을 따르고 프런트엔드는 메시지와 다시 시도 동작을 제공한다.

## 프런트엔드 경험

### 검색 상태

- `useSearchParams`로 URL의 `q`를 읽고 갱신한다.
- 검색 폼 제출은 공백을 정리한 뒤 URL을 변경한다.
- 초기화 버튼은 `q`를 제거하고 전체 좋아요 목록을 다시 불러온다.
- URL이 바뀔 때마다 검색 API를 호출하며 effect 정리 함수로 이전 요청의 늦은 응답을 무시한다.
- 시드 데이터에 맞춘 예시 검색어는 입력 편의를 위한 단축 버튼일 뿐 카테고리나 별도 순위 규칙으로 사용하지 않는다.

### 화면 상태

- 인증 확인 중과 검색 요청 중에는 명시적인 로딩 상태를 표시한다.
- 좋아요 영상이 없으면 검색 패널 대신 좋아요 추가 안내를 표시한다.
- 검색어가 있지만 일치 결과가 없으면 다른 표현을 사용하도록 안내하고 초기화 동작을 제공한다.
- API 실패는 빈 결과로 바꾸지 않고 오류 메시지와 다시 시도 버튼을 표시한다.
- 결과가 있으면 결과 수를 표시하고 각 카드 아래에 유사도 백분율, 일치 단어와 일치 영역을 표시한다.
- 모바일 폭에서도 검색 입력, 버튼과 검색 근거가 넘치지 않도록 기존 반응형 CSS를 확장한다.

## 앱 생성과 로컬 실행

- `create_app(config=None)`는 `TESTING`, `DATABASE`, `SECRET_KEY` 등 테스트 구성을 주입할 수 있다.
- 기본 데이터베이스는 현재와 같은 저장소 루트의 `data.db`다.
- 기본 호스트는 외부 인터페이스가 아닌 `127.0.0.1`이다.
- 디버그 모드는 기본적으로 꺼지고 명시적인 환경변수로만 켠다.
- 시드 데이터는 검색 예시가 재현되도록 사용자별 좋아요 관계를 결정적으로 생성한다.
- 런타임 검색은 Python 표준 라이브러리만 사용하므로 모델 다운로드와 추가 ML 바이너리 의존성이 없다.
- 런타임 패키지는 `requirements.txt`에 유지하고, Python 테스트용 pytest는 새 `requirements-dev.txt`에서 런타임 요구사항과 함께 설치한다.
- React 테스트에는 Vitest, jsdom과 React Testing Library를 `frontend/package.json`의 개발 의존성으로 사용한다.

## 오류 및 안전성

- 사용자 ID는 요청 인자가 아니라 서명된 Flask 세션에서만 얻는다.
- 좋아요 후보 집합은 검색 전에 현재 사용자 ID로 제한한다.
- 공개 영상 응답은 기존 `features.videos.api.view`를 재사용해 원본 반응 사용자 목록을 제거한다.
- 검색어는 SQL이나 파일 경로에 삽입하지 않고 메모리 내 토큰화에만 사용한다.
- 입력 길이와 결과 수를 제한해 비정상적으로 큰 단일 요청을 막는다.
- 로컬 전용 앱이므로 운영 배포용 OAuth, 외부 스토리지와 다중 인스턴스 문제는 다루지 않되 기본 네트워크 바인딩을 loopback으로 제한한다.

## 테스트 전략

### 검색 엔진 단위 테스트

- 제목 일치가 설명 또는 채널명 일치보다 높은 순위를 만든다.
- 한글과 영문의 대소문자, Unicode 정규화와 구두점이 일관되게 처리된다.
- 부분 단어의 문자 2-gram 겹침이 관련 결과를 찾는다.
- 무관한 검색어는 결과를 만들지 않는다.
- 빈 검색어는 최신순 전체 목록과 `score: null`을 만든다.
- 같은 점수는 생성일과 ID로 안정 정렬된다.
- 매칭 단어와 필드가 사용자에게 노출 가능한 형태로 생성된다.

### Flask 통합 테스트

- 비로그인 요청은 401을 반환한다.
- 로그인 사용자는 자신이 좋아요한 영상만 받는다.
- 같은 검색어라도 사용자별 좋아요 집합에 따라 결과가 달라진다.
- 좋아요가 없거나 일치 결과가 없으면 정상적인 빈 `items`와 `total: 0`을 반환한다.
- 검색어와 limit 경계값 및 오류 응답을 검증한다.
- 응답에 원본 `likes`, `dislikes` 배열이 없는지 확인한다.
- 기존 로그인, 반응 토글과 좋아요 목록 흐름이 유지되는지 검증한다.

테스트는 임시 SQLite 파일을 사용하며 실제 `data.db`와 `uploads/`를 변경하지 않는다.

### React 테스트

- URL의 `q`가 입력과 API 요청에 반영된다.
- 폼 제출과 초기화가 URL 및 결과를 갱신한다.
- 로딩, 좋아요 없음, 검색 결과 없음과 오류 상태를 구분한다.
- 결과 수, 점수와 검색 근거가 렌더링된다.
- `/recommend` 호환 경로가 `/liked`로 이동한다.

네트워크 경계만 제어하고 실제 컴포넌트, Router와 화면 동작을 검증한다.

### 최종 검증

1. Python 전체 테스트 실행
2. React 전체 테스트 실행
3. React 프로덕션 빌드 실행
4. `static/app`에 옛 `/recommend` 화면이 남지 않고 새 좋아요 검색 화면이 포함됐는지 확인
5. Flask 로컬 서버에서 데모 로그인, 좋아요 목록, 검색, 초기화와 오류 상태 브라우저 스모크 테스트
6. Git diff 및 생성 파일 점검

## 호환성과 전환

- `/api/videos/liked`는 다른 소비자를 위해 기존 목록 API로 유지한다.
- 옛 `/api/recommend/` 전체 영상 추천 엔드포인트는 제거하고 README에는 새 `/api/recommend/liked`만 공개한다.
- 옛 `/recommend?q=...` 링크는 검색어를 보존해 `/liked?q=...`로 이동한다.
- DB 스키마 마이그레이션은 필요하지 않다. 기존 `videos.likes` 배열을 그대로 사용한다.
- 기존 사용자의 `data.db`와 업로드 파일은 유지된다.

## 문서화

README는 프로젝트 목적을 TubeLite 내부 좋아요 스마트 검색으로 명확히 설명하고 다음을 제공한다.

- Python 및 Node 요구 버전
- 가상환경 생성, 의존성 설치, 시드, 프런트 빌드와 서버 실행 명령
- 데모 계정과 재현 가능한 검색 예시
- Python 및 React 테스트 명령
- TF-IDF 검색 방식과 한계
- 외부 YouTube 및 클라우드 서비스가 포함되지 않는 로컬 전용 범위
